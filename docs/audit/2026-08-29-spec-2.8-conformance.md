**Started:** 2026-08-29 · **Status: IN PROGRESS — 14 of 24 criteria verdicted** · **Scope:** read-only.

Does the code do what `docs/SPEC.md` §2.8 (Booking & Payment) and §2.10 (Reservations) say it does.
§3.3 (cancel cascade) and §3.4 (disputes) are deliberately **out of scope** — booking-adjacent, not

**This file is the audit's state.** The work stops every time it finds a flaw in the spec, and

### Resuming this

**Start from current `main`, and run `npm run check:audit` before you trust a line number.** Every
citation here was checked against the tree at the time it was written, and line numbers drift. If one
does not say what this document claims, trust the code and correct the document — one wrong citation
in an audit is worse than a missing one, because it reads as verified.

**That paragraph used to be the whole mechanism, and it did not work.** It was written on 2026-08-31
and broken the same day: PR #869 (DEC-164) added a net 23 lines to §2.8, this branch merged after it

failed. So the rule is now a gate — `scripts/check-audit-citations.mjs` pins a citation as a line
*plus the text that must be on it*, which makes a moved line a mechanical correction and a **changed**
line a stop-and-re-read. It reports its own coverage, because it pins about a third of what this
document cites and a gate that implied more would be the same failure wearing a checkmark.

**It is not in `npm run verify`, deliberately.** The pinned lines cover roughly 40% of `docs/SPEC.md`,
which every booking task edits, so wiring it into the universal gate would hard-fail unrelated PRs
whose authors have never heard of this file. Run it yourself when you pick the audit up.

Three findings here were fixed by work that shipped **while the audit was open**, on separate

**Two mistakes this document already made**, recorded so the next reader knows the failure modes

**Method.** The unit is one normative claim, not one subsection — §2.8.4a alone stacks several

`UNPROVEN` is a separate verdict from `BUILT` on purpose. §2.8 was written **after** the code it
describes, so "there is code that does this" and "something would catch it breaking" have come
apart, and collapsing them is how a retrofitted spec launders itself.

## Decisions taken during the audit

Recorded here because each one changes how later criteria read.

**1. §2.8.1 is the authority; the code is incomplete.** (operator, 2026-08-29)

`src/domain/entities.ts:615` is `export type ReservationStatus = "booked" | "cancelled"` — two
states where §2.8.1 (`:1488-1501`) specifies four. Nothing writes anything else: `write-booking.ts:136`
writes `booked`, `cancel-reservation.ts:136` writes `cancelled`, and the Xola importer's own type at
`src/import/import-reservations.ts:70` is the same pair. `pending` and `expired` appear nowhere in
the repo outside `docs/SPEC.md`. No decision record designs them and no migration writes them; the
`reservations` table (`db/migrations/0001_init.sql:81`, `status` at `:88`) types it as free text under the
no-CHECK posture, so the column would accept them and nothing puts them there.

`eventId` (`entities.ts:619`) is non-nullable, where §2.8.2 makes null-until-confirm *"the contract,
not a convenience"*.

**2. The `checkout_holds` table goes; the `pending` reservation replaces it.** (operator, 2026-08-29)

`CheckoutHold` (`src/domain/entities.ts:703-745`, table from
`db/migrations/20260718142705_claim_hold_mutex.sql:33`, DEC-109) is the built design. §2.8 forbids it
twice — *"Nothing else claims a slot"* (`:1503`) and *"No separate hold object"* (`:2014`).

Every property of the hold has a §2.8 home on the pending row:

| Hold property | Where §2.8 puts it |
|---|---|
| Mutex — unique index on `(vessel_id, date, time)` | the hull-day lock, §2.8.3 `:1521-1524` — **broader**; slot identity is what let 13:30 and 14:00 both through (`hull-busy.ts:4-9`) |
| Lazy expiry, no cron (`entities.ts:718`) | §2.8.8 `:1829` — *"every reader tests `pending AND expiry > now`"* |
| `holderToken`, matched by possession (issue #575) | §2.8.5 `:1742-1743` — opaque httpOnly cookie, *"never the typed email or phone"* |
| Explicitly **not** the authority (`entities.ts:713-715`) | the pending row **is** the authority |

The work that survives is DEC-109's lazy-expiry rule, the possession-token rule and the overlap fix
— all three already restated in §2.8. Dropping the table is a consolidation, not a loss of design.

**3. Duration vocabulary.** (operator, 2026-08-29)

| Term | Means | BrewBoat |
|---|---|---|
| **hold minutes** | the whole time a boat is committed to one departure — on the water and back at the dock | 120 |
| **trip time** | how long the customer is actually on the water | 100 |
| **turnaround** | the boat sitting at the dock between trips; hold minutes minus trip time | 20 |

Turnaround is **not stored** — it is the difference. Occupancy is measured with **hold minutes** and
never with trip time. "Hold" on its own stays reserved for the checkout hold row, so a duration is
never called a hold.

These three are owed entries in `docs/dictionary.yml` with `trip length` registered as a forbidden
alternate of `trip time`. That turns `npm run verify` red on every remaining occurrence in the
gate's corpus (`docs/SPEC.md`, `docs/decisions/*.md`, `CLAUDE.md` — not the rest of `docs/`), which
is the gate working. Register the term and run `npm run check:dictionary` to enumerate; do not
sweep by hand.

## Spec flaws

Flaws in `docs/SPEC.md` itself. Each pauses the audit and ships as its own fix task.

### Flaw #1 — occupancy is specified in trip time, and must be hold minutes

**Status: FIXED in the spec 2026-08-29 (DEC-161). The code defect stands.** Criteria #3, #4 and #5
are unblocked for audit; #4 now names hold minutes and carries the 13:30-versus-15:15 case.

`Offering` carries two durations. `entities.ts:356` `tripLengthMinutes` — *"Minutes on the water
(12.8) — display config; the customer sees '1h 40min'"*. `entities.ts:358` `holdMinutes` —
*"Minutes the boat is held per departure, **turnaround included**"*.

Occupancy must be measured with the second. Everything measures it with the first:
`claim.ts:203`, `availability.ts:400`, `availability.ts:424`, `write-booking.ts:117`.

`holdMinutes` is read by **no occupancy decision**. It round-trips through the whole stack — the
admin form and its validation (`src/admin/offering-admin.ts:34,170,215`), the repository both ways
(`src/adapters/postgres-repository.ts:264,1160`), and a contract test that pins the round-trip
(`src/adapters/repository-contract.ts:1215,1222`). The operator can set it and it is stored
faithfully. Nothing measuring a hull ever asks for it. Both duration fields are commented
"Display/config", which is presumably why neither was wired to occupancy.

*(An earlier draft of this paragraph said `holdMinutes` was "read nowhere" and appeared twice in the
repo. That was wrong in the same way DEC-161's first draft was wrong, and caught the same way — by
review. The claim the finding actually needs is about occupancy, not about existence.)*

**And §2.8 reproduced the bug** — in the wording DEC-161 replaced. §2.8.3 said a reservation occupies
*"the hull for the **trip's duration**"*, and §2.8.4a froze *"the **trip length**"*. Built exactly as
written, the new design would have carried the same defect as the old one.

**Neither sentence is in the tree, and the quotes above are the record of the flaw rather than
citations.** §2.8.3 now reads *"What a reservation occupies is the hull for the trip's hold
minutes"* (`:1519`), and §2.8.4a carries *"Also frozen: both durations"* (`:1638`).

**Failure, with BrewBoat's real numbers.** Trip time 100, hold minutes 120, departures every 120.
A 13:30 departure occupies 13:30–15:30 in reality. The code measures 13:30–15:10.

- *Latent today.* On one offering at 2-hour spacing the next published departure is 15:30, which was
  free anyway, and off-grid times are refused (§2.8.3 `:1537`). The error never fires.
- *Live on the second offering.* Another offering with a 15:15 departure on that hull reads free at
  15:10 and sells. Two parties, one boat, twenty minutes apart.

§2.8.3 anticipated exactly this case and then measured it with the wrong number. Its replacement says
the right thing — *"Each row is measured by its own hold minutes, not the asking offering's"*
(`:1540`).

**Fix, as landed (DEC-161):** §2.8.3 measures with hold minutes; §2.8.4a freezes hold minutes
**and** trip time, because the customer is quoted the water time and occupancy needs the
commitment; §2.8.1 and §2.8.8 store a reserved time and derive expiry rather than storing it;
§2.10.2's frozen booking carries both durations. Three dictionary terms registered.

**One thing deliberately not done.** `trip time` is registered **without** `trip length` as a
forbidden alternate. Registering it produced 13 failures, five of them in DEC-041, DEC-077 and
DEC-145 — all three frozen at `docs/decisions-baseline.txt:50,86,139`, where editing a record fails
the build and the sanctioned fix is converting it to schema v1 and deleting its baseline line. That
is three separate jobs. The eight `docs/SPEC.md` occurrences were corrected regardless, so the spec
is right; only the catching of a future relapse waits. (operator, option (a), 2026-08-29)

## Criterion findings

### Criterion 1 — off-grid, out of season, already departed — **PARTIAL**

Two of the three guards are built and proven. The third does not exist. Both negative assertions —
no row, no payment — hold.

| Guard | State | |
|---|---|---|
| off the schedule grid | **BUILT** | `claim.ts:171` → `isOnScheduleGrid` → `unbookable: "off_schedule"` |
| outside the season | **BUILT** | same predicate — `availability.ts:145` compares against `seasonStart`/`seasonEnd` |
| **already departed** | **NOT BUILT** | nothing, anywhere — issue #824 |
| no row written | **BUILT** | a refusal returns at `claim.ts:154-173`, before `acquireCheckoutHold` |
| no payment created | **BUILT** | `create-departure-payment-intent.ts:98-104` returns before pricing or the intent mint |

**Grid and season are one predicate, not two.** `isOnScheduleGrid` (`availability.ts:135-148`)
checks four things in sequence: the date parses, it round-trips (so `2026-09-31` cannot roll into
October and pass the weekday check for the wrong day), it falls inside the season, its weekday is
one the offering runs, and the time is a published departure. That is worth knowing because it
corrects the refusal table under Criterion 5 below.

Proven: `claim.test.ts:177` refuses a date outside the season using **2026-09-05, a Saturday past
`seasonEnd`** — right weekday, wrong season, so it isolates the season check from the weekday one.
`claim.test.ts:185` covers the weekday. `create-departure-payment-intent.test.ts:115` is named *"an
off-grid slot is refused before any hold or Stripe call (#799)"* — which is this criterion's second
half, tested. And `claim.test.ts:164`'s docstring states the invariant directly: *"A rejection
writes NO hold row."*

**Already departed is absent, and it is worse than a missing edge case.** `claim.ts` calls `now()`
exactly twice, at `:177` and `:293`, both for hold expiry. Neither compares the clock to the
departure. `availability.ts` takes a `dateRange` from its caller and never refuses a past date on
principle — `:385-386` intersects that range with the season and nothing else.

The failure is not someone crafting a past date in a URL. **A 13:30 departure is still on the grid,
still in season, still on the right weekday at 15:00 that same afternoon**, so today's already-sailed
departures stay bookable and chargeable for the rest of the day, through the ordinary calendar. That
is issue #824, confirmed at the source, and the same-day case is the one that will actually happen.

### Criterion 2 — a row before Stripe, and that row alone clears the departure — **PARTIAL**

The first half holds in a different shape. The second half is true only of the departure's own slot.

**A row is written before any Stripe call, and it is a `CheckoutHold`, not a `pending` reservation.**
`create-departure-payment-intent.ts:94` acquires the hold; the PaymentIntent is minted at `:144`.
A refusal returns at `:98-104`, before either. So the ordering property the criterion asks for is
real — decision 2 changes which row it is, not whether there is one.

**The read path sees a hold, and `/book` uses it.** `app/(public)/book/page.tsx:91` reads
`listLiveCheckoutHolds(asOf)` and passes them into `deriveVirtualAvailability` at `:173`;
`availability.ts:439` renders the slot `held`. Lazy expiry applies on this side too — `:333` tests
`h.expiresAt > input.asOf`, so a stale row is inert. Covered by `availability.test.ts:578`, `:587`,
`:596`, `:601` and `:612`.

**But a hold clears only its own slot, and the write refuses more than that.**
`availability.ts:334` keys held slots on `slotIdentity(vesselId, date, time)` and `:431` looks them
up by exact identity. A live hold on Brew 4 at 13:00 marks 13:00 `held` and leaves **13:30 on the
same boat reading `available`**, even though the hull is committed until 14:40.

The write does not agree. `claim.ts:245-248` measures rival holds by **overlap**, so it refuses the
13:30 the calendar just advertised. That is **issue #826** — *"the calendar and the write disagree
about what a hold occupies"* — confirmed at both lines.

**And it is the exact case `hull-busy.ts:20-21` claims is impossible:** *"shared by
`deriveVirtualAvailability`, `candidateVessels`, and the write CAS, so the read path and the
backstop cannot disagree about what 'busy' means."* True of **events**, which both sides run through
`busyIntervalsFor`. False of **holds**, which never reach those functions on the read path — the
sharing guarantee is scoped to a type that holds are not.

**Untested rather than enshrined.** No test on the read path covers a hold overlapping a *different*
time on the same hull. The nearest, `availability.test.ts:622` — *"a hold on a DIFFERENT slot
doesn't touch this one"* — uses a different **date** (2026-07-11 against 2026-07-04) and is
correct as written. The overlap case simply has no test, on either side of the divergence.

### Criterion 3 — one sale across two overlapping departures — **BUILT**

The hull-day lock exists and is the right shape. `postgres-repository.ts:1440-1442` takes
`pg_advisory_xact_lock(hashtext('<vesselId>|<date>'))` as step (0) of `saveBookingIfSlotFree`,
before the overlap query, released with the transaction. Its comment gives §2.8.3's own reasoning:
a row lock cannot help, because the rival row is a phantom until it inserts.

**It is the transaction-scoped variant, and that matters in production.** `docs/DEPLOY.md:28` says
`DATABASE_URL` is the pooled PgBouncer endpoint used by app queries, and `:149` says PgBouncer
discards session state between transactions. A session-scoped `pg_advisory_lock` would break there.
`pg_advisory_xact_lock` holds, because a pooler pins a connection for the life of a transaction.

Proof: `postgres-repository.test.ts:439-492`. Real Postgres, two `saveBookingIfSlotFree` calls in one
`Promise.all`, 13:30 and 14:00 on one hull, asserting exactly one `won` **and** asserting `count = 1`
on the data rather than on the return values. The docstring names its own negative control. It ran —
`npm run verify` reported `2384 passed (2384)`, passed equal to total, so nothing was skipped and
`dbUp` was true.

**Three things that survive this verdict**, each of which becomes live under decision 2:

1. **The overlap predicate reads one table.** `postgres-repository.ts:1449` is `select 1 from events`.
   Today a checkout hold is caught separately in `claim.ts`. Once a `pending` reservation is what
   occupies the boat and materializes no `Event` (§2.8.2), the write CAS looks at `events`, sees
   nothing, and sells a boat somebody is mid-checkout on. The lock would serialize it perfectly and
   the answer would still be wrong.
2. **The predicate coalesces on `events.duration_minutes`**, filled from
   `offering.tripLengthMinutes` at `write-booking.ts:117`. Hold minutes has to be frozen onto the
   `Event`, not only onto the reservation.
3. **The lock is advisory, so it binds only callers who ask.** Exactly two places take it —
   `postgres-repository.ts:1440` and `:1083`. Nothing in the database stops a third write path from
   skipping it, and that discipline currently lives in comments.

Note against the criterion's own wording: it says *"repeatedly"* and the test runs the race once.
Deterministic given the lock, so this is a note, not a defect.

### Criterion 4 — each row measured by its own duration — **PARTIAL**

Three of the four paths are right and one is not.

| Path | Measures rivals by | |
|---|---|---|
| `busyIntervalsFor` (`hull-busy.ts:92`) | each event's own `durationMinutes ?? XOLA_TRIP_MINUTES` | correct |
| write CAS (`postgres-repository.ts:1457`) | `coalesce(duration_minutes, XOLA_TRIP_MINUTES)` per row | correct |
| `availability.ts:400` | the materialized event's own duration | correct |
| **`claim.ts:221`, rival holds** | **`tripMinutes` from `claim.ts:203` — the ASKING offering** | **wrong (issue #825)** |

`CheckoutHold` (`entities.ts:727-745`) carries `offeringId` but no duration, so the claim path has
nothing to measure a rival by without a lookup that does not exist. The comment at `claim.ts:220`
says *"A hold's own offering sets its trip length"* and the code does the opposite.

**The test that should catch this cannot.** `claim.test.ts:336-355` is named *"skips a boat whose
overlapping departure is already held by a rival"* and reads as coverage for exactly this rule. Its
rival hold is created with `offeringId: OFF` — **the same offering the buyer is asking for**
(`claim.test.ts:348`). With one offering, "its own length" and "the asking offering's length" are the
same number, so the test passes identically under the bug and under the fix. There is no test
anywhere in `src/reservations/` that puts two offerings with different durations on one hull.

**And every path above measures trip time, not hold minutes** — flaw #1's code side, unfixed
everywhere. So even the three correct rows are correct about the wrong quantity.

### Criterion 5 — the calendar and the write refuse the same set — **NOT MET**

They refuse different sets, and the difference is enumerable.

| Refusal | Read (`availability.ts` + `claim.ts`) | Write (`writeSlotBooking` → `saveBookingIfSlotFree`) |
|---|---|---|
| offering missing / not live | `claim.ts:154-155` | — |
| invalid guest count | `claim.ts:156` | — |
| off the schedule grid | `claim.ts:171` | — |
| ~~out of season / wrong weekday~~ | **correction:** also `claim.ts:171` — the season is inside `isOnScheduleGrid` (`availability.ts:145`), not read-path-only as first written. See Criterion 1 | — |
| party does not fit the hull | `candidateVessels` | — |
| operator block | `candidateVessels` | — |
| a rival's live hold | `claim.ts:245-248` | — |
| hull busy over the departure | `hullIsBusy` (TypeScript) | the SQL predicate at `postgres-repository.ts:1448` |
| **already departed** | **nothing** | **nothing** — issue #824 |

`writeSlotBooking` (`write-booking.ts:88-153`) performs **no** grid, season, block, fit or departure
check. It builds the candidate `Event` from the request and calls the CAS. The only guard inside the
hull-day lock is the events-overlap query.

**This is an ordering difference from §2.8, not just a missing check.** §2.8.4 step 3 puts the
off-grid, out-of-season, already-departed and overlap refusals *inside* the hull-day lock, at the
moment the `pending` row is written. The code checks grid, season, blocks and fit at **hold**
time, unlocked, in `claim.ts`; then takes the lock minutes later, at webhook time, and re-asks only
one of them. §2.8.6's *"Nothing is re-validated at confirm"* sanctions that for **confirm** — but in
the code there is no locked pending-write between the two, so those checks are never inside a lock
at all.

**The two overlap implementations are separate code.** `hull-busy.ts:20-21` states the guarantee:
*"Shared by `deriveVirtualAvailability`, `candidateVessels`, and the write CAS, so the read path and
the backstop cannot disagree about what 'busy' means."* That is true of the in-memory adapter
(`in-memory-repository.ts:598-610`, which calls the real functions) and **false of Postgres**, which
reimplements the arithmetic as SQL — `split_part(time, ':', 1)::int * 60 + …` at
`postgres-repository.ts:1454-1457`.

So the guarantee as *stated* — one shared function — holds in the adapter that never runs in
production and not in the one that does.

**But the behaviour is pinned even though the code is not**, and the first draft of this finding
missed it. `repository-contract.ts:709`, `:724` and `:767` run `saveBookingIfSlotFree` against
**both** adapters and assert the overlap outcomes, including the `#691` overlapping-time case. The
two implementations therefore cannot silently diverge on anything the contract covers. They already
differ on malformed input, which it does not cover — `hull-busy.ts:86-88` blocks the whole day and
the SQL has no equivalent branch.

**What is genuinely unpinned is the read-versus-write comparison**, which is what this criterion
actually asks for. The contract suite pins write-against-write across adapters. Nothing anywhere
asserts that the calendar and the write refuse the same set, and given the refusal table above they
demonstrably do not.

### What the operator pause changes here (2026-08-29, issue #864)

Operator-caused change and customer-caused change are different problems and only one is code. A
rival customer taking the hull is what the lock exists for. An operator blocking a boat or editing a
schedule mid-checkout is answered by pausing reservations, not by re-validating settings across the
checkout-to-webhook gap.

So of the refusals missing from the write path, the settings-shaped ones — block, season, grid, fit
— are **covered by the pause** and are not defects. What remains a real gap is the overlap re-check,
which the code already does, and the already-departed check, which is a clock rather than a setting
and is absent from both sides (issue #824).

### Criterion 6 — a pending reservation's `eventId` is null until booked — **NOT BUILT**

`docs/SPEC.md:2057`. The first ⚠ criterion verdicted, and it does not resolve the way the other eight
are likely to. **The literal criterion is not built. The guarantee it exists to protect holds anyway,
by a mechanism the criterion does not describe, and nothing tests it.**

**Nothing here is a defect to fix today.** The verdict column says NOT BUILT because the entity the
criterion names does not exist; it does not mean the crew manifest is currently leaking in-flight
checkouts. It is not. What follows is where the protection actually comes from, and what happens to
it under decision 2.

**The literal half, which decision 1 had already settled.** `entities.ts:615` is
`"booked" | "cancelled"` — no `pending`. `entities.ts:619` is `eventId: EventId`, no `?`, so the
field cannot hold null. There is no pending reservation, so there is no `eventId` on one to be null.
Nothing new is established by re-deriving that here; it is restated because a reader arriving at
criterion 6 from the table should not have to find it under "Decisions taken".

**The half that is new: no `Event` is materialized before the payment succeeds.**

| | |
|---|---|
| `writeSlotBooking` is what creates the `Event` | `write-booking.ts:87` |
| its only non-test caller is the webhook | `booking-webhook.ts:361` |
| the live checkout entry point mints a PaymentIntent and parks a hold, and writes no reservation | `create-departure-payment-intent.ts`, called from `app/(public)/book/checkout/actions.ts:166` |

Both checkout entry points say so in their own comments, in the same words — *"The SLOT — no eventId
(the Event doesn't exist yet; the webhook materializes it)"* (`create-departure-payment-intent.ts:170`,
`create-departure-checkout.ts:149`).

So §2.8.2's actual requirement — *"An abandoned checkout therefore materializes nothing"*
(`:1512`) — is satisfied. It is satisfied by there being **no row at all** in the interval, with the
`CheckoutHold` holding the boat, rather than by a pending row whose `eventId` is null. That is
decision 2's substitution seen from the other end: the criterion describes the destination, and the
current code reaches the same place by the road it is being asked to leave.

**Which makes §2.8's own stated stake worth re-reading.** `:1908-1910` says the crew manifest *"is
protected today only because a pending reservation has no `eventId`"* — *"one careless line from being
lost, and it is why the null is a contract."* Today the protection is stronger than that and rests
somewhere else: the manifest reads reservations by event, and before payment there is neither. The
sentence is written about the design being built, not the code running, and a reader checking it
against the tree will find it describes neither state exactly.

**Nothing pins any of it — this is the finding with a cost.** Two tests look like they cover it and
do not:

- `create-departure-payment-intent.test.ts:94` and `create-departure-checkout.test.ts:83` both assert
  `metadata.eventId` is `undefined`, each with the comment *"no Event yet"*. They assert the absence
  of a **key in the Stripe metadata payload**, which is a different claim from the absence of an
  `Event` **row**. Both would pass unchanged if the checkout materialized an Event and simply declined
  to name it to Stripe.
- `create-departure-checkout.test.ts:72` is named *"acquires a hold on the smallest fitting boat and
  carries the SLOT (no eventId)"*. The name is honest about the metadata payload; it is the two
  comments that over-read it.

There is **no assertion anywhere that no `Event` exists between checkout and payment.** Every
`getEvent(…)` in the reservations suite that runs on this path is a post-webhook
`.not.toBeNull() // materialized` — `create-departure-payment-intent.test.ts:256`,
`create-departure-checkout.test.ts:123,201,202`. The two negative `getEvent(…).toBeNull()` in the repo
are elsewhere and unrelated (`import-reservations.test.ts:57`, `repository-contract.ts:844`). Nor does
anything assert that a successful checkout leaves zero reservations: the
`listAllReservations()).toHaveLength(0)` assertions at `create-departure-payment-intent.test.ts:336`
and `:347` are webhook-refusal cases, not the pre-payment interval.

By this document's vocabulary the behaviour is `UNPROVEN`, and it is the kind of thing `UNPROVEN`
exists to name: the code does the right thing, the tests would not notice it stopping.

**Where this lands when decision 2 goes in.** The guarantee changes hands. Today it holds because no
row exists; afterwards it holds because a row exists with a null `eventId` — precisely the "one easy
line" §2.8.2 warns about (`:1514-1517`), and the moment at which the field becomes populatable. The
test that does not exist today is the one that has to exist before the pending row does, or the
protection is silently handed from a structural impossibility to a convention nobody checks.

### Criterion 7 — abandoning checkout leaves nothing and sends nothing — **UNPROVEN**

`docs/SPEC.md:2058`. **All four halves hold, and the reason they hold is structural rather than
guarded: the checkout path writes exactly one row and reads everything else.** The first verdict in
this audit where the code is right and the only finding is that nothing would notice it going wrong.

| What must not exist | Why it doesn't |
|---|---|
| an `Event` | `writeSlotBooking` has one non-test caller, `booking-webhook.ts:361` — see §Criterion 6 |
| a customer record | `resolveCustomerId` is called from `write-booking.ts:122` and `import-reservations.ts:256`. Both are post-payment or Xola import; neither is reachable from checkout |
| a booking code | `ensureBookingCode` (`ensure-booking-code.ts:49`) takes a `reservationId`. Its callers are `app/lib/booking-confirmation.ts:58` and `:117` and `recover-booking-link.ts:98` — all of which need a reservation that does not exist yet |
| anything sent | every sender is a `WebhookDeps` field — `alertPaidButUnbooked`, `notifyCustomerSoldOut`, `sendConfirmation` (`booking-webhook.ts:68,76,84`). Call sites are in `booking-webhook.ts` **and one in `confirm-booking.ts:48`**; every one of them is downstream of a *succeeded* PaymentIntent, which an abandoned checkout never produces |

**The checkout path is reads plus one write.** `create-departure-payment-intent.ts` calls
`getOffering` (`:89`, `:116`), `listEvents` (`:119`), `getVessel` (`:132`) and `getPaymentConfig`
(`:141`), then acquires the hold. Nothing else touches the repository. So the four absences are not
four guards that could each be forgotten — they are one property of the path, which is a much stronger
position than the criterion asks for.

**Nothing sweeps, so abandonment has no code path of its own.** Hold expiry is lazy and read-side
(DEC-109): `availability.ts` and `claim.ts` test `expiresAt` when they look. There is no job, and
therefore no place a notification could be attached. Abandoning a checkout is the absence of a second
event, not an event.

**One thing this audit cannot settle from the repo, and it is the only real gap.**
`create-departure-payment-intent.ts:166` sets `receiptEmail` on the PaymentIntent when the customer
gave an email, and its own comment says *"Absent ⇒ Stripe sends no receipt; present ⇒ it does, in live
mode regardless of the account's email settings."* Whether Stripe sends anything for an intent that
never succeeds is **Stripe's behaviour, not ours**, and it is not answerable by reading this
codebase. The expected answer is no — a receipt follows a successful charge — but "sends nothing to
**anyone**" is a claim about a third party here, and this document does not assert third-party
behaviour it has not read the documentation for. Verifying it is one look at Stripe's receipt docs,
and it should be done before this criterion is called `BUILT`.

**An abandoned checkout does leave a `CheckoutHold` row**, and that is not a violation. The criterion
enumerates four things and a hold is none of them. It is worth naming because criterion #9 asks for
the **opposite** — that an abandoned checkout survive on disk as an `expired` reservation carrying
slot, party size and reserved time. The hold row is what will be measured against that, and under
decision 2 the two criteria converge on one row.

**Nothing tests any of it.** No test in the suite abandons a checkout. The four assertions that come
closest are all about something else:

- `resolve.test.ts:91` and `:201` assert `listCustomers()).toHaveLength(0)`, but both are about a
  **phone number that will not parse** — the first over five bad inputs, the second confirming a
  booking still succeeds without a customer link. Neither involves an abandoned checkout.
- `availability.test.ts:587` (*"an EXPIRED hold contributes nothing"*) and `claim.test.ts:357`
  (*"an EXPIRED overlapping hold does not occupy anything"*) do exercise expiry — but they pin the
  **slot coming free**, which is criterion #8. Neither looks at events, customers, codes or sends.

So the verdict is `UNPROVEN` in its purest form: the code does the right thing for a structural
reason, and the suite would be equally green if a future refactor moved `resolveCustomerId` up into
the checkout path.

### Criterion 8 — the trip comes free the instant the window passes — **BUILT (by the hold, not the pending row)**

`docs/SPEC.md:2060`. **The second `BUILT` in this audit, and the first one where the test does the
hard half.** There is no sweeper to stop, both paths compute expiry at read time, both adapters
implement it, and the contract suite pins the boundary to the millisecond across both.

**Read the qualifier before reading the verdict.** This criterion, unlike #6, names no object — it
says a trip comes free when a window passes, and is indifferent to what holds the trip. That is why
it can return `BUILT` where #6 could not. But §2.8.8 behind it is not indifferent: it says *"every
reader tests `pending AND expiry > now`"* (`:1829`), and every reader today tests
`hold.expiresAt > now`. **Built, and not to the spec.** A bare `BUILT` would read as "nothing to do
here", and that is wrong — decision 2 moves all four comparison sites onto a different table and the
boundary test has to be rewritten against it. What survives is the *design*: lazy expiry, no job, one
comparison, both adapters, the boundary pinned. What moves is every line that implements it.

**"With the sweeper stopped" is trivially satisfied, because there is no sweeper.** Three cron routes
exist — `app/api/cron/doorbell-tick`, `tick`, `xola-pull` — and none of them reference
`CheckoutHold` in any form. Nothing scheduled deletes or expires a hold.

**Expiry is one comparison, and both sides make it the same way.**

| | |
|---|---|
| read path | `availability.ts:333` — `h.expiresAt > input.asOf` |
| write path | `claim.ts:215` skips on `h.expiresAt <= at0`; `:266` requires `h.expiresAt > at0` |
| Postgres | `postgres-repository.ts:1727` — `select * from checkout_holds where expires_at > $1` |
| in-memory | `in-memory-repository.ts:763` — `h.expiresAt > asOf` |

Same boundary in all four: a hold is dead at exactly its `expiresAt`, not one tick later. That is
what "the instant" asks for, and it is not an accident of one implementation — `claim.ts:211` names
the rule as DEC-109's and says it is the deriver's.

**There IS a sweep, and finding it is what makes the verdict interesting rather than a formality.**
`acquireCheckoutHold` deletes expired rows — `repository-contract.ts:1106` is named *"acquireCheckoutHold
sweeps EVERY expired hold, not just its own slot (issue #713)"*, and `:1128` pins that it *"never
touches a LIVE hold on another slot."* So cleanup exists; it rides the next write instead of a
schedule. **Correctness does not depend on it**, because every reader already filters by `expiresAt` —
the sweep reclaims storage, not availability. That is precisely the shape §2.8.8 asks for, arrived at
without a job to stop.

**The proof is the boundary, and it runs against both adapters.** `repository-contract.ts:1102-1103`:

- `listLiveCheckoutHolds("2026-07-01T12:15:00.000Z")` → **0**, on a hold expiring at 12:15
- `listLiveCheckoutHolds("2026-07-01T12:14:59.999Z")` → **1**

One millisecond either side of the instant, asserted. `runRepositoryContract` is invoked twice —
`postgres-repository.test.ts:94` and `in-memory-repository.test.ts:9` — so this is pinned against
**real Postgres**, not only the test substrate. The Postgres half is gated on `dbUp`
(`postgres-repository.test.ts:84`); the last full run reported `2412 passed (2412)`, passed equal to
total, so nothing was skipped.

**This is the answer criterion #5 wanted and did not get.** There, the read and write overlap
predicates were separate code and the guarantee was scoped to a type holds are not. Here the two
adapters *are* separate code — SQL against an in-memory filter — and the contract suite is what stops
them diverging. Same risk, actually pinned.

**The ⚠ on this row was removed, and the verdict carries the warning instead.** The marker means a
criterion is *written in* `pending`/`expired` vocabulary the code does not have, and this one is not —
it names no state. But that definition turned out to be narrower than what a reader wants the marker
for, because "will be rebuilt when decision 2 lands" is true here and the marker could not say it. So
the qualifier went into the verdict column rather than widening ⚠ across rows nobody has re-read.
Eight of the twenty-four remain marked. **If a later pass widens the marker's meaning, this row is the
first one to revisit.**

**One narrow divergence the contract does not cover.** Postgres compares a timestamp column against a
cast parameter; the in-memory adapter compares ISO strings **lexically**. Those agree for
`Z`-suffixed strings at fixed millisecond precision, which is the only shape the test uses and the
only shape `now()` produces. They would disagree on an `asOf` written `+00:00` instead of `Z`, or
without milliseconds — lexically `"…00.000Z" > "…00+00:00"`, where as timestamps the two are equal.
Latent, not live, and unpinned. Worth one assertion if anyone ever widens what may be passed as
`asOf`.

### Criterion 9 — an abandoned checkout survives on disk — **NOT BUILT**

`docs/SPEC.md:2061-2063`. **NOT BUILT for the same reason as #6: the entity does not exist.** The row
this criterion describes is an `expired` **reservation** — `SPEC.md:1500`, *"The payment window ran
out. A state, not a deletion (2.8.8)"* — and there are no `pending`/`expired` states (decision 1). So
nothing to keep, because nothing is written.

*(An earlier draft of this section led with "the row the spec wants kept is the row issue #713 was
written to delete." That is wrong and worth recording as a failure mode: #713 deletes **holds**, and
§2.8 removes the holds table outright. Different rows in different tables. The real relationship is
narrower and appears at the end of this section — the two decisions solve the same **problem**
oppositely, which is not the same as one deleting the other's data.)*

**The nearest thing today is a hold, and it does not survive either.** `CheckoutHold`
(`entities.ts:727-758`) carries
`vesselId`/`date`/`time` (the slot), `guestCount` (party size), `createdAt` (the reserved time) and
`expiresAt`. Every field criterion 9 asks for already exists on the object that already holds the
boat. Nothing needs designing.

**Then the next acquire deletes it — every expired hold, everywhere, not just the one being
replaced.** `postgres-repository.ts:1680` is
`delete from checkout_holds where source='muster' and expires_at <= $1`, and
`in-memory-repository.ts:738-742` is the same loop. Pinned by `repository-contract.ts:1106`,
*"acquireCheckoutHold sweeps EVERY expired hold, not just its own slot (issue #713)."*

**The sweep's own comment explains why, and it is a good reason.**
`postgres-repository.ts:1671-1674`: *"Scoped to the slot identity, an abandoned checkout on a
departure nobody re-attempts was unreachable by any cleanup path and grew the table without bound;
there is no scheduler in this codebase, so an acquire is the only moment a sweep can happen."*

**§2.8 solves the same problem and reaches a different answer, which is the useful comparison.** #713
had no scheduler available, so it deleted at the only moment it could — an acquire — and had to delete
*everything* expired to catch rows nobody would ever re-attempt. §2.8 assumes a job exists and splits
the work in two, which is what lets it keep the data: the **sweeper** relabels and *"never deletes,
and this is load-bearing rather than tidy"* (`:1846`), and a separate **reaper** *"runs rarely, on a
long horizon, and deletes old `expired` rows so the table does not grow without bound"* (`:1841`).
Same unbounded-growth problem, answered with a retention horizon instead of immediate deletion.

**So the query the criterion names is not a query.** *"How many checkouts were started and walked
away from last month"* cannot be answered from this database — the rows are gone, deleted by the next
person to start any checkout on any boat. Nothing archives them first: **there is no hold history
table.** `grep -rl checkout_holds db/migrations/*.sql` returns five files — the create
(`20260718142705_claim_hold_mutex.sql:33`), a token column, an index, a foreign-key era change and
the refund-leases migration that cites the pattern — and none of them creates an archive. And
`audit_events` (`0024_audit_events.sql:1`) is the **crew** log — add/drop/change keyed on
`crew_member_id`, per DEC-118 — with no reservations writer anywhere in `src/reservations/`.

*(That claim first cited `ls db/migrations/*checkout_hold*` as "three files". It returns **two**, and
the glob does not match the migration that creates the table, because that one is named
`claim_hold_mutex`. The conclusion survived; the evidence for it did not. Third absence claim in this
document to arrive with bad evidence, which is the pattern rather than the incident.)*

**The data does exist, at Stripe.** `create-departure-payment-intent.ts:94` acquires the hold and
`:153` mints the PaymentIntent, so every abandoned checkout leaves an intent behind. What Stripe
retains and for how long is Stripe's, not readable here — the same discipline criterion 7 applied to
`receiptEmail`. But the shape is the §2.8.5 finding again: **a thing §2.8 wants on our own row is
currently only at the payment provider.**

**What is actually missing: two of three mechanisms, and the one that exists is on the wrong object.**

| §2.8.8 asks for | Built today |
|---|---|
| **the clock** — the window passes, the boat is free immediately, nothing has to run (`:1829`) | **yes** — on `CheckoutHold`, verdicted BUILT under criterion #8 |
| **the sweeper** — relabel a lapsed `pending` row to `expired`, never delete (`:1833`, `:1846`) | **no.** There are no `pending`/`expired` states to relabel between |
| **the reaper** — rare, long horizon, deletes old `expired` rows (`:1841`) | **no** |

So the build is not "keep the row instead of deleting it." It is a status union, a nullable `eventId`,
and two jobs — and §2.8.8 attaches a rule to each that is easy to lose. The sweeper *"never labels a
row it cannot prove was unpaid"* (`:1836`): a row with a payment id belongs to the reconciler, or a
webhook outage lasting longer than the payment window turns a paying customer into an `expired` row.
And an `admin`-sourced pending row is exempt from all of it (`:1823-1827`, DEC-163) — no window, never
swept — which a reader has to branch on **first**.

**The reaper's horizon is the retention policy and §2.8 gives no number** (`:1841` says only "rarely,
on a long horizon"). That is the correct posture for a value the host's env owns, but it means the
period is undecided, and it is the single knob trading table size against how far back the operator
can ask the question this criterion exists to answer.

*(An earlier draft of this paragraph claimed §2.8 had no answer to the unbounded growth #713 closed,
and that building §2.8 would silently revert it. Both false — `:1841-1844` is that answer, and it
additionally names distinguishing scripted abuse from real abandonment as part of the build. The
error came from reading §2.8.8's title, "Expiry is a clock, not a job", and stopping there; the
subsection goes on to specify two jobs.)*

**The second clause is true of the built system and false of the spec, and the difference is the whole
point of the criterion.** (operator, 2026-08-31: *"we do not have a mechanism to check abandoned
checkouts, so that question doesn't make any sense."* — correct about today.)

*"…and how long did each hold a boat?"* is unanswerable now, because abandonment is silent: it is the
absence of a second event, nothing marks a hold as abandoned, and the row is deleted anyway. **§2.8
knows exactly what the clause is for**, and says so at `:1846-1856`. The payment window can be wrong in
two directions and only one is already visible:

- **Too short** — real buyers cancelled mid-payment. Each leaves a refund and a sold-out message, so
  the operator already sees it.
- **Too long** — hulls tied up for people who were never going to buy. Visible *"**only** if expired
  rows survive, carrying their slot, party size and reserved time."*

That asymmetry is the reason the sweeper never deletes. The duration is the payment window on every
row, which is exactly what makes the **count** meaningful: forty abandoned checkouts times a
fifteen-minute window is ten hours of hull nobody could buy, and that number is the instrument for
deciding whether the window is too long. **So this clause is not a report to build — it is the
justification for retention**, and the thing to preserve when someone later argues the expired rows
are clutter.

### Criterion 10 — a retry is matched by the cookie token — **BUILT (by the hold, not the pending row)**

`docs/SPEC.md:2064-2065`. **The best-built thing this audit has found, and the only criterion so far
whose hardest half is satisfied by construction rather than by a check.** Same qualifier as #8: the
criterion says *reservation* and the object is a `CheckoutHold`, so decision 2 moves it.

| The criterion asks | Where |
|---|---|
| reuses the same hold on a retry | `claim.ts:262-270` — matched before the fit-and-fallback loop runs |
| at its **original** reserved time | `claim.ts:281` comments it and `:284` does it — `mine` is returned unmodified from the array read once at `:186`, never recomputed |
| matched by the **cookie** token | `app/(public)/book/checkout/actions.ts:101-110` — `httpOnly`, `secure`, `path: "/"`, 30-minute `maxAge` |
| **not** by email or phone | `DepartureHoldRequest` (`claim.ts:120-134`) **has no email or phone field** |

**The last row is the finding.** §2.8.5 forbids matching on typed identity (`:1742-1746`), and the code
does not merely avoid it — the claim path never receives those fields at all. There is no guard to
forget and no branch to get wrong, which is a stronger position than the criterion asks for. It is the
same shape as criterion #7: a property of the path rather than a check on it.

**And it is stronger still, because the token is a session id in everything but name.**
`holder-token.ts:26-27` mints 32 bytes of CSPRNG as base64url; `:32` validates against an anchored
`/^[A-Za-z0-9_-]{43}$/` so a crafted cookie cannot arrive as a lookalike. The cookie is `sameSite:
"lax"` rather than `Strict` for a documented reason — *"the 3-D Secure return from Stripe is a
top-level GET navigation, which Lax sends and Strict would drop, losing the token exactly when the
customer comes back to finish"* (`actions.ts:103-105`).

**This was built the wrong way first, and that history is the evidence.** `holder-token.ts:4-11`
records it: the first cut keyed reuse on the buyer's **email or phone**, and `/security-review` killed
it. Two exploits fell out — *"supply a victim's email and you were handed their hold and a
PaymentIntent on the boat they were buying; supply it with an absurd guest count and the
fit-revalidation branch deleted their hold outright."* So §2.8.5's *"It must never be the typed email
or phone"* is not a precaution written in advance; it is a rule this codebase earned.

**Two conditions on reuse that the criterion does not ask for and that matter more than it does.**
Both are in `claim.ts` and both close holes a naive reading would leave open:

1. **A token is required on both sides** (`:257-259`). A tokenless hold is never reused and never
   matches another tokenless hold — otherwise two pre-cookie sessions would match on `undefined ===
   undefined` and share a boat. Pinned by `claim.test.ts:498`, *"two sessions with NO token never
   share a hold."*
2. **A reused hold gets the same scrutiny a fresh one would** (`:271-280`) — `candidates` re-applies
   fit and blocks, `vesselIsAvailable` re-applies booked and hull-busy. The comment names the case:
   an operator blocking a vessel for a mechanical fault at 10:00 would otherwise hand the 10:02 retry
   that same boat and take payment for it. *"The world can change inside a 15-minute hold."*

**Six tests, and the negative controls are the useful half.** `claim.test.ts:397` (same hold, not a
second boat), `:410` (*"does NOT extend the expiry — a retry cannot park a boat indefinitely"* —
whose assertion at `:421` is deliberately **outside** the type guard, because *"with every assertion
inside the type guard, a regression that returned `soldOut` would run zero expects and pass green"*),
`:439`
(a retry that no longer fits takes a bigger boat and leaves the old hold alone), `:498` (tokenless
never share), `:513` (an expired hold of the same buyer is not reused), `:524` (a hold from a different
trip is not reused).

**The gap, and it is in the plumbing rather than the logic.** **Nothing tests `mintHolderToken` or
`isHolderToken`** — no test file anywhere imports either. The ten `holderToken` mentions in the unit
suite are split five and five between `claim.test.ts` and `create-departure-payment-intent.test.ts`,
and both pass fixture strings through to matching; neither mints or validates one. Nor does anything
assert the cookie's attributes: `httpOnly`, `secure` and `sameSite` are set in one server action and
pinned by nothing — a repo-wide search for those attribute names finds no assertion outside
`actions.ts` itself, so a refactor could drop `httpOnly` and every test would stay green. The
criterion's own subject — the matching — is well covered; its delivery mechanism is not.

*(The sentence above first said all ten mentions were in `claim.test.ts`. They are 5/5 across two
files. The conclusion was right and the attribution was wrong — **the fourth time in this document
that an absence claim has arrived with faulty evidence**, and this time inside the paragraph meant to
be careful about exactly that. The pattern is now clear enough to state as a rule: in this document,
run the search again before writing the sentence that describes it.)*

### Criterion 11 — `payment_failed` does not expire the reservation — **UNPROVEN (vacuously)**

`docs/SPEC.md:2066`. **The first criterion satisfied by nothing existing, and the first where passing
tells you nothing.** It is a *negative* — a requirement that something not happen — and a system with
no handler, no state to move it to, and no operation to move it with satisfies every negative it is
asked. That is worth a verdict of its own rather than a `BUILT` a future reader would take as
reassurance.

**Three independent reasons it cannot happen, none of them a guard.**

```
$ grep -rn "payment_failed" --include=*.ts src/ app/
(no output)
```

1. **No handler.** The adapter normalizes Stripe's shape into a domain union and recognizes four
   families — `checkout.session.completed` (`stripe-payment.ts:194`), `charge.refunded` (`:209`),
   the three `charge.dispute.*` (`:235-237`) and `payment_intent.succeeded` (`:265`). Anything else
   falls to `return null` at `:277`, which is the only fall-through in the function. The test double
   has its own normalizer (`fake-payment.ts:76`) and does not recognize the event either, so the
   suite cannot pass on a divergence between them.
2. **Nothing downstream runs.** `booking-webhook.ts:142` is `if (!event) return { handled: false }`,
   and `app/api/webhooks/stripe/route.ts:46` turns that into a 200. Verified, acked, ignored — which
   is the right posture: a non-2xx would make Stripe retry an event nobody wants.
3. **There is nothing to expire.** No `expired` state exists (decision 1) and no operation moves a
   reservation to one (criterion #9). Even a handler that wanted to do this could not.

**Whether the event even arrives is not readable from this repo**, and the codebase says so:
`route.ts:21` records that an earlier design *"rested on a Stripe dashboard nobody can read from the
repo (#544)"*. The endpoint's subscribed event list lives at Stripe. Same discipline criterion #7
applied to `receiptEmail` — this document does not assert third-party configuration it cannot read.
It does not matter for the verdict, because reason 1 holds whether or not the event is delivered.

**The nearest test exercises the path and not the claim.**

```
$ grep -rn "payment_failed" --include=*.test.ts src/
(no output)
```

`booking-webhook.test.ts:320` is *"handled:false for a non-checkout event"* and passes the literal
body `"null"` — it pins that an unrecognized event is acked rather than erroring, through a
degenerate input rather than a real `payment_failed` payload, and it asserts only the return value.
The one test that also asserts **nothing was written** (`:82-85`, reservations flag off) is a
different case. So even the ack behaviour is only half pinned.

**The forward-looking half is the reason this criterion exists, and it is not yet a hazard.** §2.8
puts it in the list because once a `pending` row exists, `payment_failed` becomes a tempting handler:
an event arrives saying this payment failed, and the obvious thing is to mark the row `expired`. That
would be wrong — a declined card is retried on the same reservation (criterion #10), so expiring on
failure destroys the row the retry needs. The guard §2.8 already writes for the neighbouring case is
§2.8.8's *"The sweeper never labels a row it cannot prove was unpaid"* (`:1836`); this criterion is
the same rule aimed at the webhook instead of the job.

**So the useful reading is: nothing to fix, and one thing not to build.** When the `pending` row
lands, the correct handling of `payment_intent.payment_failed` is still to ack and ignore it — and
that will need a test naming the event, because at that point the absence will no longer be
structural.

### Criterion 12 — a late-succeeding superseded payment — **PARTIAL**

`docs/SPEC.md:2067-2068`. **The money half is built and well tested. The identity half cannot be built
in the current shape, and the reason is the sharpest structural finding in this audit so far.**

**The relationship §2.8.5 assumes is inverted in the code.** §2.8.5 (`:1730-1733`) requires that a
reservation carry many payment ids over its life, and warns that *"one overwritable column loses the
first id and turns a late success into an unrecognisable charge."* There is no such column to
overwrite — because the arrow points the other way:

| | |
|---|---|
| `confirm-booking.ts:55` | `key: pi.paymentIntentId` |
| `booking-webhook.ts:279` | `const idempotencyKey = charge.key` |
| `booking-webhook.ts:308` | `const reservationId = reservationIdFor(idempotencyKey)` |
| `write-booking.ts:35-38` | `reservationIdFor` = `sha256(idempotencyKey)` |

**The reservation id is derived from the payment id.** So two PaymentIntents cannot resolve to one
reservation — they derive two different reservation ids, by construction. A booking payment can never
be *superseded* on a single row, because there is no single row for it to be superseded on.

**Storage is not the constraint.** `Payment` (`entities.ts:801-805`) is its own row carrying
`reservationId`, so many-payments-per-reservation is representable, and the **balance** path already
does it (`recordBalancePayment`, `booking-webhook.ts:785-799`). Post-trip gratuity deliberately does
**not** — `booking-webhook.ts:747` says *"**Writes NO `Payment`** — a Payment would inflate the 'paid'
sum and drive `balanceOwedCents` negative → a false overpay alert"* — and puts the money on its own
`Gratuity` row instead. So it is only the **booking** payment that is welded to the reservation's
identity.

**What actually happens to the late success, and it is the right outcome by a wrong road.** The
second PaymentIntent books. The first succeeds late, derives a *different* reservation id, reaches
`writeSlotBooking`, finds the slot taken — by the customer's own booking — and returns `lost`. That
lands in the DEC-109 residual-race branch (`booking-webhook.ts:507-527`): auto-refund keyed on
`refund_${charge.key}` so a redelivery cannot double-refund, plus a "sold out while you were paying"
notice, with a loud manual-refund alert as the fallback when the refund itself throws.

So the customer is refunded and nobody is charged twice. **But the system cannot tell the two cases
apart** — a stranger who lost the race and the same customer's own superseded payment take the
identical branch, and the second one is told the trip sold out while they were paying, which is not
what happened to them.

**And the money leaves no trace on our side.** `booking-webhook.ts:503` states it as a deliberate
choice: *"The money moved, and is NOT recorded here (#613 — no reservation to reference)."* No
`Payment` row is written for a losing or superseded charge, so the record that money moved and came
back exists only at Stripe. That is the same shape as the §2.8.5 finding under the sales-tax section:
a thing §2.8 wants on our own row is currently only at the payment provider.

**The refund half is tested five ways, including both failure modes** —
`create-departure-payment-intent.test.ts:350` (*"residual race on the PI path: loser auto-refunded
keyed on the PI id"*), `create-departure-checkout.test.ts:139` (two paid sessions, one booked one
refunded and notified), `:169` (**no `payment_intent` to refund → manual alert**), `:183` (**the
auto-refund itself throws → falls back to the manual alert**), and `confirm-booking.test.ts:134`
(the success page does *not* refund — that is the webhook's job), whose `:162` comment notes an
assertion added specifically to prove the test reaches the residual-race branch at all.

**The supersession case IS tested — under another name, and what it pins is the behaviour §2.8 calls
wrong.** `create-departure-payment-intent.test.ts:350` is named for the residual race and its comment
at `:353` says *"Both buyers minted intents for the SAME small boat."* But `:356` builds **one**
metadata object and replays it for both events:

```js
const m = pay.intents[0]!.metadata;
const first  = await processBookingWebhook(deps, piEvent("pi_fake_1", 27570, m), FAKE_SIGNATURE);
const second = await processBookingWebhook(deps, piEvent("pi_fake_2", 27570, m), FAKE_SIGNATURE);
```

Same customer name, same email, same slot — **only the PaymentIntent id differs**, which is exactly
one buyer with two payment attempts. `create-departure-checkout.test.ts:143-144` is the same shape:
`slotCompleted()` hardcodes the customer and is called unmodified for both session ids. Nothing in the
outcome logic reads customer identity anyway — `write-booking.ts:92-94,151-152` decides `already`
versus `lost` purely on `getReservation(reservationIdFor(idempotencyKey))`.

So the criterion's own case runs on every suite. **What the test asserts is
`{ handled: true, outcome: "lost" }` and a refund** — it pins the payment *failing* to resolve to a
reservation, which is the current behaviour and the opposite of what this criterion requires. The
test is not wrong; it documents the built design faithfully. But it means the gap here is not
coverage. It is that the covered behaviour is the one §2.8 replaces, and the test will have to be
rewritten rather than added to.

*(An earlier draft of this paragraph claimed the opposite — that every residual-race test is two
different buyers and the supersession case is untested. That was wrong, and it was **the fifth
faulty absence claim in this document, written one criterion after adopting the rule against exactly
this**. The grep for `supersed` returned nothing and I let a word search stand in for reading the
fixtures. The rule was "write the command and its output"; the failure mode it did not cover is
running a command that answers a different question than the sentence does.)*

**What it costs when decision 2 lands.** §2.8.6's `confirmReservation(paymentId)` finds the pending
reservation *by the payment id recorded against it*, which is a lookup, not a derivation. That is a
different identity model from the one built, and adopting it means the reservation id stops being a
function of the payment — which in turn is what makes the deterministic `ON CONFLICT (id)` idempotency
at `write-booking.ts:32-33` work today. **Whatever replaces it has to carry that weight**, or the
redelivered-webhook double-write this hash currently prevents comes back.

### Criterion 13 — killing the webhook still books from the success page — **BUILT**

`docs/SPEC.md:2069`. **Unqualified, and the only criterion so far that the code cites back.**
`app/(public)/book/success/page.tsx:5` opens *"**This page CONFIRMS the booking** (issue #827, SPEC
§2.8 criterion 13)"*, and `confirm-booking.test.ts:86` is named
*"books a succeeded PaymentIntent, given only its id and no webhook at all"* — the criterion, in a
test title, asserting the criterion.

**It was built because the old reasoning was right about the premise and wrong about the conclusion.**
`page.tsx:6-10` records it: the page used to be static copy, on the reasoning that a redirect is not
proof of the write and the webhook is what books. True — *"and wrong about the conclusion: it left
`payment_intent.succeeded` as the ONLY path that ever books, so a delayed or misconfigured endpoint
meant the customer had paid and nothing had happened, with no bound on when anyone would notice."*

**The redirect is still not trusted.** Stripe appends `payment_intent` and `redirect_status` to the
return URL and both are text in an address bar, so `confirmBookingByPaymentIntent`
(`confirm-booking.ts:87-95`) resolves the id **against Stripe** —
`deps.payments.getSucceededPaymentIntent(paymentIntentId)` at `:91` — and returns `ignored` on
anything Stripe does not report as succeeded.

**And the adapter checks the status, not merely that the intent exists**, which is the difference
between the claim holding and not: `stripe-payment.ts:160` is `if (pi.status !== "succeeded") return
null`, with a `catch` returning `null` at `:167-169`. A forged id that happens to name a **real but
unpaid** intent resolves to `null` and books nothing — the case a bare existence check would have
missed.

**Failure is swallowed on purpose**, and the reasoning is worth keeping: `page.tsx:52-56` catches
everything, because *"a customer who paid should never see a stack trace because our fast path
failed, and the webhook is still coming for exactly this case."* The page is the fast path; the
webhook is the guarantee. Neither is load-bearing alone, which is the shape the criterion asks for.

**Five tests, and three of them are negative controls:**

| `confirm-booking.test.ts` | |
|---|---|
| `:86` | books from the PI id alone, **no webhook at all** — this criterion |
| `:103` | idempotent — the webhook landing afterwards produces no second booking |
| `:121` | refuses a PaymentIntent Stripe does not report as succeeded — *"the redirect is not proof"* |
| `:134` | does **not** refund or notify on a residual-race loss; that stays the signed webhook's job |
| `:169` | does **not** book the metadata-less intent behind a hosted balance checkout |

`:134` matters beyond this criterion: `confirmBookingByPaymentIntent` passes
`notifyOnResidualRaceLoss: false` (`confirm-booking.ts:93-95`), so a public page cannot trigger a
refund or a sold-out notice. Compensation belongs to the signed webhook only.

**One gap, disclosed by the code itself and verified rather than repeated.** `page.tsx:25-29` names
issue #831: *"`saveBookingIfSlotFree` reports who observes the row, not who inserted it, so two
callers racing inside the same instant can both be told `booked` and both send the customer their
booking link."* That is accurate. `postgres-repository.ts:1563-1567` decides the outcome with
`select 1 from reservations where id=$1` and `won.rowCount === 1` — a **read after** the write, not
an insert rowcount — and `:1351` records the limitation as deliberate. `write-booking.ts:151-152`
does the same on the other side, distinguishing `already` from `lost` by re-reading.

**The defect is pre-existing and this page makes it likelier**, which is exactly how the docstring
characterises it. **The duplicate is a second notification, not a second sale**, and that is two
citations rather than a reassurance: `booking-webhook.ts:453` gates `sendConfirmation` on
`result.outcome === "booked"` alone — *"never the idempotent `already` … or the customer gets
re-texted on every retry (DEC-122)"* — so a caller told `already` sends nothing, while a caller
wrongly told `booked` does. And the money write is insert-only against a deterministic id
(`in-memory-repository.ts:515` — *"Insert-only … a payment row is immutable once written, so a
re-delivered webhook is a no-op, not an overwrite"*), so the racing caller's `savePayment`
is a no-op. One sale, one Payment row, potentially two texts.

So it does not touch this verdict, but it is the thing to fix before a third confirm caller is ever
added. The race window is `write-booking.ts:92-94`'s early `getReservation` check, which is TOCTOU
against a concurrent caller holding the same reservation id.

### Criterion 14 — closing the browser still books, via the webhook — **BUILT**

`docs/SPEC.md:2070`. **Criterion #13's twin from the other side.** #13 asked whether the page books
without the webhook; this asks whether the webhook books without the page. The answer is one test:
`booking-webhook.test.ts:126` calls `processBookingWebhook` alone — no browser, no success page, no
client anywhere in it — and asserts the reservation is written, the `Payment` recorded with its
amounts and both Stripe ids, and `sendConfirmation` fired **once** with the freshly-booked row.

**"Produces a booking" has to mean one the customer can reach, and it does.** The webhook path mints
the booking code before composing the message (`app/lib/booking-confirmation.ts:58`, *"there is no
link to send without one"*) and sends over email and/or SMS (`:43-44`). A customer who closed the tab
gets their link without ever loading a page.

**Two degradations, both deliberate and both leaving the booking intact.** If neither channel is
configured, `:45-52` logs and returns — booked, unnotified, and loud only in a production deploy. And
a throwing `sendConfirmation` is swallowed rather than bubbled, because a 500 would make Stripe retry
the whole event; pinned by `booking-webhook.test.ts:292`, *"a throwing sendConfirmation never breaks
the committed booking (best-effort, DEC-122)."* Both fall back to the operator's resend, which
`booking-confirmation.ts:57` names as the recovery.

**The boundary the criterion does not reach.** "At the moment of payment" splits in two. If the
browser closes *after* Stripe captures, the webhook books — that is this criterion and it holds. If it
closes *before* the payment succeeds — mid-3DS, say, which `checkout-form.tsx:189-193` sets up with a
`return_url` — then no payment succeeded, and booking nothing is correct rather than a gap. Which of
the two Stripe reports for any given card is Stripe's behaviour and is not readable here; the audit
only claims that a **succeeded** payment books with no client involvement.

## Sales tax — and the thing standing next to it

Opened because **DEC-107** is titled *"Sales tax is read live, not frozen onto the booking"* while
§2.8.4a freezes every component. That reads as a live contradiction from the index. It is not, and
saying why matters more than the flag did.

**DEC-107 is already retired.** `status: "superseded"`. So the record does not contradict the spec;
it records a position the spec replaced.

**But nothing says what replaced it.** `superseded_by` is unset, and no decision in the tree declares
`supersedes: [DEC-107]` — `grep -rln "supersedes:" docs/decisions/*.md | xargs grep -l "DEC-107"`
returns nothing. `CLAUDE.md`'s convention is a pair: the new record carries `supersedes`, the old one
flips to `status: superseded`. Half of that pair happened. **`npm run check:decisions` passes**, so
the pairing is not enforced — a record can be marked dead with nothing pointing at what killed it,
and the gate is content. That is a record-integrity gap, not a reservations one, and it is likely
not unique to DEC-107.

**And the booking path does freeze the tax.** `create-departure-payment-intent.ts:133` computes
`taxCents` once at checkout from `config.taxRateBps` and never recomputes it. DEC-107's live read
was about the **balance** path, which §2.8.10 already documents as dormant and non-conforming. So
the contradiction I flagged from the title was wrong about scope, and the honest finding is
somewhere else — three lines further down the same file.

### Where the frozen money actually goes — **NOT MET**, and this is the serious one

Every frozen component is written into **Stripe metadata**, and §2.8.5 forbids that in as many words:

> For the human reading the Stripe dashboard, `description` — a first-class Stripe field — carries
> the offering, the trip, the party size and who booked. **So the booking charge sends no
> metadata at all.** Empty is a rule that can be checked; "send some but never read it" is a
> discipline that decays.

`create-departure-payment-intent.ts:160-181` sends **eighteen** metadata keys: `purpose`,
`offeringId`, `vesselId`, `date`, `time`, `guestCount`, `priceCents`, `extrasCents`,
`gratuityCents`, `gratuityBps`, `serviceFeeCents`, `kind`, `taxCents`, `customerName`, `email`,
`phone`, `waiverConsentAt`, `waiverVersion`. That is the entire booking — the slot, the money and
the customer — with Stripe as the store of record between checkout and confirm.

`booking-webhook.ts:612-619` reads it back to build the reservation. §2.8.14 names this too: *"No
booking assembled from data Stripe hands back."*

**The failure mode is silent and it is money.** The read is
`Number(charge.metadata.taxCents ?? 0)` — a metadata key that is missing, truncated or dropped
produces a booking recorded with **zero tax**, and nothing raises. Same shape for `gratuityCents`
(`:614`) and `serviceFeeCents` (`:618`), where a lost key means crew money and operator revenue
quietly reading zero.

This is **issue #812** — *"Retool the Stripe payment workflow — a booking must not depend on
metadata surviving the round trip."* Confirmed, and the audit adds the specific defect: the
defaulting is what turns a transport problem into a wrong number rather than an error.

It also explains why §2.8.5 puts the payment id on **our** row and reads nothing from the payment
object but its id and status. The freeze is supposed to live on the reservation. Today it lives at
Stripe.

## Spec gaps — things §2.8/§2.10 never said

Not conformance findings. The code does not disagree with the spec here; the spec is silent. Found
while auditing, and recorded with the operator decisions already taken so they survive a window
ending. Each is its own spec task with its own decision record.

The spec was written after the code and was never finished. These three are what that produced.

### Gap A — there is no admin booking surface

**Nothing in `app/(admin)/` creates a reservation.** No `writeSlotBooking`, no `saveReservation`, no
reservation construction anywhere in the admin tree. The admin surfaces are purchases, calendar,
blocks, customers — all of which read or modify bookings that already exist. So the operator cannot
take a booking over the phone at any notice, at any price.

**Why it was missed, which the design doc explains without meaning to.**
`docs/design/reservations-admin.md:31` says the surface set was enumerated from the Xola seller UI
screenshots — *"experiences/schedules config, purchases list + detail, dashboard, event detail pane,
customers/contacts."* Xola has a book-for-a-customer flow; it is not one of the captured screens, so
it never entered the enumeration and every document downstream inherited the hole. It was not lost
in the shuffle — it was never written down.

Decisions taken (operator, 2026-08-29):

- **The admin sends a payment link.** The reservation is written, holds the boat, and stays `pending`
  until the customer pays. **No card is read over the phone** — a card field on an admin form
  defeats SAQ-A, which applies precisely because card numbers never reach our servers.
- **No other payment methods.** No cash, no "already paid elsewhere". Everything goes through Stripe,
  which also keeps §3.3's refund path intact.
- **`source` stays `"muster"`.** `entities.ts:566` is `"xola" | "muster"` and `:563` notes widening is
  one line, but there is no use case for telling an admin booking from a web one. Not added.
- The payment window for a phone booking probably wants to be longer than the public one. Open.

### Gap B — the booking cutoff

**A length of time before a departure during which the public cannot book it.** Measured backwards
from the departure. Inside it the public site refuses; the admin surface (Gap A) still books.

Decisions taken (operator, 2026-08-29):

- **A system setting, in `app_settings`** — the key/value table from
  `db/migrations/0006_app_settings.sql:18`, which already holds the `payment.%` rates
  (`postgres-repository.ts:1234`), `engine_paused` (`:2311`) and
  `self_claim_requires_confirmation` (`:2328`). A row plus a code fallback, and **the fallback is not
  the value** — same posture §2.8.4a describes for the tax rate. **No number goes in the spec.**
- **Computed, never stored.** A clock comparison at read time, like expiry — no rows, no job, nothing
  to sweep. It moves forward on its own.
- **Its own slot state**, not `blocked`. `availability.ts:410` currently renders `available`,
  `booked`, `blocked`, `unavailable`, `held`. A separate state keeps the operator's Blocked count
  honest and lets the customer be told *"too late to book online, call us"* rather than a flat
  unavailable — which only matters once Gap A means someone can take that call.
- It lands where blocks already land, on **both** paths — `availability.ts:426-429`'s precedence and
  `candidateVessels` — so the calendar and the write do not diverge again.

**Naming trap.** `docs/SPEC.md:347` already defines **booking horizon** — *"knowable far out; gates
the sale"* — which is the far end of the same axis. And `:324` carries *"a lead-time cutoff"* as an
explicitly **rejected** idea for crew asks in §1.3. The new term is **booking cutoff** and it needs a
dictionary entry to keep all three apart.

**Not the staffing horizon.** The operator picks the value by asking how much notice they want to
give crew, but the rule is not a staffing rule and must not be welded to
`STAFFING_HORIZON_LEAD_DAYS` (`src/builder/derive.ts:148`). The rationale for choosing a number is
not the definition of the number.

### Gap C — discounts

**Partial or full, applied by the operator today and plausibly by a guest promo code later.** Both
belong in one spec task.

Decisions taken (operator, 2026-08-29):

- **The discount comes off the fare-plus-extras base.** Then **tax, tip and the service fee all
  recompute on the discounted base.** The service fee explicitly follows the discount — discount the
  trip and the operator is paid less for it, so the 3% is 3% of the smaller number.
- Partial and full are both required.

**A full discount has nothing to confirm it, and this is the hard part.** §2.8.6 is
`confirmReservation(paymentId)` and it finds the pending reservation *by the payment id recorded
against it*. Comp a booking to zero and there is no payment, no id, no webhook, and no success page.
The reconciler will not find it either — it works a list of rows whose payments succeeded. So a
zero-balance booking needs a second entry point into the one function §2.8.6 exists to keep
singular, and that is a decision, not a detail.

**Also unresolved:** whether a discount is an amount, a percentage, or both; and whether it is frozen
onto the reservation like every other component in §2.8.4a (it must be).
