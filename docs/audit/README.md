## Running an audit

1. **The cloud environment must install dependencies.** Add `cd muster && npm ci` to the environment's setup script (in a cloud session: the environment menu in the title bar, then Edit). Without it the container has no `node_modules`, `npm test` fails, and the session will not install them itself, because installs are the operator's call. The crewing audit hit this and fell back to a stand-in for vitest.
2. **Write the prompt from the nearest one in `docs/audit/prompts/`.** The crewing prompt is the most complete. Every prompt carries:
   - "This message is the approved plan", and no session skills.
   - The branch or commit to audit.
   - The question, then the reverse: code that decides something where the spec is silent.
   - Where the spec is, where the code starts, and what is out of scope because another audit covers it.
   - The rules: change no code; open no pull request, file no issue, post no comment; every claim cites `path:line`; tests run as `npm test -- <file>`, never `npx vitest`, which the permission policy denies; probe tests are named `*.audit-tmp.test.ts`, reproduced in the report and deleted before commit; use subagents.
   - Severity S1–S4 defined for that subject.
   - The report: `AUDIT-<name>.md` at the root of a new `audit/<name>` branch, pushed. **Pushing the branch is the whole delivery. No pull request.**
3. **Start a cloud session on `mobiustripper42/muster` and paste the prompt.** Save the prompt to `docs/audit/prompts/<date>-<name>.md` when the report comes in.
4. **When the report lands, bring it into this folder** on a docs branch:

   ```
   git fetch origin audit/<name>
   git show origin/audit/<name>:AUDIT-<name>.md > docs/audit/<YYYY-MM-DD>-<name>.md
   ```

   Add a row to [Done](#done), add its findings to the [ledger](#ledger), and open a docs pull request. Once that merges, the `audit/<name>` branch can be deleted.

## Fixing findings

- **Work from the ledger, S1 first.** Pick one row, read the finding in its report, then **re-read the code it cites on current `main`** — the line numbers are the audited commit's, and the code may have moved or already changed.
- **Each finding ends in exactly one status:**
  - `open` — not yet looked at.
  - `fixed — pull request #N` — the pull request that fixes it.
  - `issue #N` — real work bigger than one sitting. One issue may cover several findings; name them all in the issue, and give each its row's status.
  - `dismissed — <why>` — not a defect, or not worth fixing. The reason is required.
  - `duplicate of <audit> <id>` — the other row carries the work.
  - `check — <what>` — a known reason to think it is already fixed; confirm, then set a final status.
- **The pull request that fixes a finding updates its ledger row in the same diff.** Then `main` says `fixed` exactly when the fix has merged. A ledger that says "fixed" about a branch that never merged is how an earlier project's audit lied about itself (`scripts/check-docs.mjs:7-14`).
- **A fix is an ordinary task.** A behaviour change is specced in its issue and built with `/build-task`; a stale comment or spec sentence can go straight in. Several small S4 fixes can share one pull request.
- **Filing is not the default** (`.claude/CLAUDE-context.md` § Median gaps): if the fix is smaller than writing the issue, fix it.

### Pattern 1 — Money moves in four steps, everywhere

**The hole:** we ask Stripe to move money, something breaks halfway, and nothing written down says what was being done. The customer is owed, refunded twice, or told the wrong thing, and nothing finishes the job.

**The rule (operator, 2026-11-22):** every path that moves money does all four.

1. Write down what is about to happen, before calling Stripe.
2. Call Stripe with a fixed key taken from that record, so asking twice cannot move money twice.
3. Write down the result. Until it is written, the record is unfinished, and no screen says what happened unless it is known.
4. A job finds unfinished records, asks Stripe what happened, and finishes them.

**Where it exists:** the balance charge, all four (`src/reservations/balance-charge.ts`, DEC-202). Booking payments have the first three; the fourth is the reconciler (`docs/SPEC.md` §2.8.9), not built: issue #1236. Refunds have neither the first nor the fourth.

**Keeping it plugged (proposed, not in the codebase):** a check that fails when anything outside the one module calls a Stripe method that moves money, so a new path cannot skip the steps. Today refunds are called from `src/reservations/refund-payment.ts` and `src/reservations/booking-webhook.ts`.

**When:** Feb 1. **Rows:** paired PS-1 (silent S1-1), silent S2-1 (paired PS-9, silent S3-7), money F3, F5, F20 and U2, conformance C15 and C19. **Also:** paired PS-3 and PS-5, plan S2-1. **Proposed by triage:** silent S3-4, S3-5, S3-6, S3-8, S3-21, S4-2 and S4-5, paired PS-22. **Issue:** issue #1278. It builds on issue #1236 (F3, F20), and the spec decides whether it replaces or widens issue #1240 (F5, U2).

### Pattern 2 — Check that it can still be paid for, right before the money moves

**The hole:** a link or a form opened earlier is paid after the trip stopped being sellable: cancelled, blocked, or already sailed.

**The rule (operator, 2026-11-22):** one check, run before Stripe is called and again before the customer is handed a way to pay: the booking is still payable, its slot is not blocked, and the trip has not started. If it fails, nothing is charged.

**And when money lands anyway** (operator, 2026-11-22): a check cannot catch a customer already on their bank's approval screen. Money that lands on a booking that cannot take it is recorded, refunded automatically, and the customer and the operator are told. The refund goes through pattern 1.

**When:** Feb 1. **Rows:** operator OR-1, OR-2 and OR-3, silent S2-2, paired PS-2, money F2. **Proposed by triage:** silent S4-7. **Issue:** issue #1279. The spec decides whether it replaces or widens issue #1237 (F2).

### Pattern 3 — Nothing says it happened until it is known (ruled)

**The hole:** a screen or a message is fixed text, and the send behind it threw away whether it worked. Someone is told "we've sent your request" or "the crew have been told" when nobody was.

**The rule:** a send returns its real result, and the message is made from that result. A screen says "sent" only if it was. The model is re-sending a confirmation, which reports each channel (`app/(admin)/admin/calendar/[reservationId]/actions.ts`).

**Feb 1, customers (issue #1282, operator 2026-11-23):** silent S2-3, S2-5 and S2-7, paired PS-4. **May 1 (operator, 2026-11-23), crew and the operator:** silent S2-6, S2-9, S2-10, S2-11, S2-12, S2-15 and S2-17. **Existing issues:** issue #1239 (F4, and silent S2-4, a confirmation nobody retries) and issue #1263 (silent S2-8, nothing notices the cron tick stopping).

### Pattern 4 — Two saves that should be one (proposed; hold until something breaks)

**The hole:** one thing is saved, the next save fails, and what is left is half a change that nothing finishes. A retry makes it worse or is refused.

**The rule (proposed):** the two are saved together or not at all, and people are told after. Where they cannot be saved together, the order is the one that fails safe.

**When (proposed):** after release, once something actually breaks this way: every one of these needs a failure at the wrong moment. **Rows:** silent S2-13, S2-16 and S2-18, paired PS-6, PS-11 and PS-16. **Also:** paired PS-8, the one that is not crew.

### Pattern 5 — The same legality check at every way into a seat (ruled)

**The hole:** tapping Yes, a cancelled shift coming back and a merge each skip the check that someone may legally crew the seat, or run part of it. Self-claim runs all of it (`src/asks/claim.ts`).

**The rule (operator, 2026-11-23):** every way into a seat runs the one check. The override keeps its scope: issue #587 was closed by the operator's ruling that credentials are inside it. The override refuses the same person twice on one boat (S1-3); triage's reading is that this is not a credential check but one body in two seats, so it sits outside issue #587's scope.

**When:** May 1. **Rows:** crewing S1-1, S1-2 and S1-3 (the override seating one person twice), and S1-5 (a confirmed person who goes on PTO, takes the day off or is archived: at four boats the operator cannot hold which shifts that person held, so those shifts are surfaced; ruled 2026-11-23, replacing the one-boat ruling at `docs/SPEC.md:581` and DEC-119's candidate-gate scope for this case). Crewing S1-4 is issue #560.

## Ledger

Statuses are `open` unless a row says otherwise. A "same finding as" or "overlaps" note on an untriaged row is an import-time lead, not a verdict: triage confirms it, sets one row to `duplicate of …`, and buckets the pair once, at the higher of the two severities. IDs are each report's own; refer across audits as "money F5" or "crewing S2-7".

**When** is the deadline a finding has to be fixed by, set when it is triaged: `Feb 1` (before the Reservations release), `May 1` (before guests and crew are on the water), `after release`, or `—` (not triaged, or nothing left to fix). It stays when the finding is filed, so a phase plan can pick up every `Feb 1` row that is not `fixed`.

**The triage rule (issue #1230, operator, 2026-11-20):** `Feb 1` is anything on the reservations side that can lose money — money taken with no booking, a refund missed or wrong, a wrong charge or tax. `May 1` is anything guests or crew hit on the water, crew pay included. `after release` is the rest.
