What this asserts — argue with it

  • A block is an availability subtraction (DEC-125), not a per-event flag. That's the whole difference from Xola: you don't hunt down and toggle each departure — you state the closure once at its natural scope and the calendar removes what it should.
  • Three scopes, three real use cases: Location (river closed → everything launching there, a date + time window) · Vessel (boat out of service → all its slots, a date range) · Hold (reserve a boat for a private thing → one slot, no customer event).
  • This is the single registry — the anti-Xola. Xola had ~3 places to create blocks with zero visibility between them; you'd get blindsided by a block you forgot in another screen. Here, every block is visible in one list regardless of where it was made. Creation stays split by what's natural — scoped blocks (location window, vessel range) created here; single-slot ones (hold, one-off blackout) made on the calendar where you're looking at the slot — but a single-slot block still shows here read-only, with "On calendar →" to act on it. Visibility is unified even though creation isn't.
  • Every block shows its impact — "removes N slots" — before you commit and in the list after. You see what you're taking off the calendar, which Xola never told you.
  • Blocks are reversible. "Lift" puts the slots back. Nothing is destroyed; a block is a layer over the schedule rule, not an edit to it.
  • A Hold is not a reservation. It reserves the boat with no customer `Event` — the slot renders Held on the calendar (distinct from Open / Sold). This is the "reserve a boat for a special event but don't make an actual event" case.
  • Booked trips inside a block are a list, not a workflow. The block is authoritative (the boat IS out), so you create it without pre-resolving. The conflicting trips hang off the block row (expand) as a plain list, each linking to its reservation — resolution happens there, not here (operator's call: this doesn't happen often; just show which ones and let me deal with them). The block is Clean / N to resolve / Resolved.
  • Crew fall out automatically. You only work the customer side. Moving or cancelling a trip mutates its Event → formShifts re-derives → the blocked boat's shift cancels, the new boat's shift crews itself, and affected crew are notified. That's the reconciliation path hardened in v1.0.15 — solid downstream of this screen.
  • Creating a conflicting block warns first — "removes N open slots · M booked trips ($X) conflict" — so you see the money before you commit, then work the list on your own clock.
  • A Location block blocks everything there (operator, 2026-07-17) — no per-offering carve-out. Block the location, nothing sails from it for that range; there's no "block one offering at this dock but not another." Keeps a block a single, legible date-range subtraction instead of a matrix.
  • No recurring blocks — make N (operator, 2026-07-17). "Every Monday for two months" is a reach; the operator creates the handful of blocks they actually need. Revisit only if the manual count ever gets painful, which at BrewBoat's cadence it won't.
