What this asserts — argue with it

  • Re-send, never reveal. The link is a bearer token (DEC-122) — anyone holding it can manage the booking. So the form never shows the booking or the link from typed input; it re-sends the existing link to the contact already on file. Typing someone's email + last name can't hand you their booking.
  • Same primitive as crew auth. This is the magic-link-resend we already have for crew login, pointed at reservations. No new mechanism.
  • Neutral confirmation — "if we found a booking." The after-submit screen is identical whether or not there was a match, so it never confirms who booked. No "no booking found for that email" (that leaks existence).
  • Match fields: email-or-phone + last name (operator-confirmed 2026-07-17) — enough friction to be non-trivial, low enough that a real customer clears it.
  • Sends to both channels on file (email + SMS), since we don't know which the customer still has — matches the confirmation's dual-channel send.
  • Repeat customers, one link. We have repeat guests, so one contact holds several reservations. The re-sent link lands on the current / next reservation; past trips are reachable from there (the manage page lists them). The link resolves to the active booking, history is a click away.
  • Settled 2026-07-17: recovery is rate-limited (~6/hour) to stop link-fishing (a system setting). Bearer-token reach — one link surfacing a contact's full history — is accepted (same person), a conscious DEC-122 loosening to record.
