Reservation calendar — does it scale?

The v2 grid is clean because it assumes one offering, 4 boats, one shared set of times. Here's the same day stress-tested: 6 boats, three offerings with different times (Cruise 11:30/1:30/3:30/5:30/7:30 · Lite 12:00/2:00/4:00/6:00 · Duffy rental 8:30/11:00), and a blackout. Below: the current boat × time grid vs. a resource timeline. Same data, both.

Layout A

Boat × time grid — the current v2 model, stressed

Once times stop lining up, the shared time-rows become a union of every offering's times — 11 ragged rows, and most cells are blank because a boat only runs some of them. Six columns already feel tight; an 8th boat wraps or shrinks the pills to nothing. The grid encodes offering-times as structure, so complexity multiplies the axes.

Layout B

Resource timeline — boats as lanes, real time across

Boats are the only fixed axis; time is continuous, and the offering is just color. Ragged times sit where they actually fall, turnaround gaps become visible (you can see the empty water on Brew 3 between 1:30 and 5:30), a 7th boat is one more lane, and a new offering adds a color — never a row or column. Density stays proportional to boats × real departures, not to the catalog.

The takeaway

  • Make the axes match reality: boats are the one fixed, scarce thing → the stable axis. Time is continuous. Offering is color + a filter, never a row or column.
  • Timeline generalizes; the grid is its special case (when every offering shares the same times, the timeline just looks like the tidy grid you already have). So you lose nothing today and gain the growth path.
  • You still can't become the FareHarbor wall — you render boat-lanes, not one pill per open availability per product. Your ceiling is boats × real departures.
  • Mobile stays the time-grouped list (reservation-calendar-mobile) — a list scales past any grid; the timeline is a desktop affordance.
  • Open call: default the day view to the timeline, or keep the grid as the "consistent-times" fast view and offer timeline as a toggle when offerings diverge? Both are cheap once the data model is boats-and-time.
