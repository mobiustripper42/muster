**Four things worth remembering:**
- **`E2E_PROD` defaults to `!CI` (`playwright.config.ts:33-36`), so a bare local
  `playwright test` runs the PROD server while CI runs DEV.** Several hours of "does not
  reproduce" were measured on the wrong server and had to be discarded. The prod path also
  deterministically fails all 8 `iphone`/WebKit tests — `next start` sets `NODE_ENV=production`,
  the session cookie goes `Secure`, and WebKit refuses it over plain http. Use
  `npm run test:e2e:dev`. This is documented at `playwright.config.ts:98-104` — inside the file,
  discoverable only after losing the afternoon.
- **Reproduction scope matters as much as the loop.** `calendar:789` passes 40/40 isolated and
  42/42 as a whole file, and fails 4/4 only in the full suite. A `-g` filter is a different
  experiment from the one CI runs.
- **CPU load has to survive the shell.** The first contention run proved nothing — `&` burners
  died with the parent Bash call and `uptime` was unchanged. Start them in the same command as
  the thing under test and print `uptime` on both sides.
- **`workers: 1` / `fullyParallel: false` is load-bearing** (`playwright.config.ts:46-47`) — the
  suite shares one `muster_test` DB, so raising workers to manufacture contention would produce
  fake failures from seed stomping rather than real races.
