**The fix shrank twice, from opposite directions.** It began as the issue framed it: a
derivation-contract change needing `@architect`, because `manning: []` was thought legitimate for a
self-captained Duffy and had to be told apart from a missing vessel row. The operator's ruling that
a Duffy gets a **dock-hand** removed the only input for which `Crewed` was correct — no new state,
no `manningKnown` flag, no architect gate. Then the operator's second ruling — an empty manning rule
is an *error*, not a workflow state — turned the remaining question ("return `Pending`?") into a
throw. One line, arrived at by deleting design rather than adding it.

**19 tests failed on the first run and that was the finding.** All from `form-shifts.test.ts`'s
shared fixture, which seeded the Duffy with `manning: []` and carried a test whose entire subject was
the vacuous `Crewed`. The suite had encoded the defect as intended behaviour, which is why nothing
ever caught it.

**Two review findings accepted rather than fixed, both verified against the code first.**
`app/api/cron/tick/route.ts:98` is a bare `await tick(repo, now)` in a file where its five neighbours
each carry a `catch` + `console.error`, and the three per-shift loops have no isolation — so one bad
vessel would halt a whole run silently. And "unreachable by construction" is too strong: the catalog
screen births a vessel with `manning: []` (`vessel-admin.ts:74`) and the manning actions are
withdrawn stubs that redirect (`shift/[shiftId]/actions.ts:349-356`), so **no surface in the app sets
manning at all**. Both accepted on the operator's call: boats are made by `npm run db:seed:fleet`,
which always writes a manning rule; a boat hand-made through the catalog screen and then sold is a
firing offence, not a design target. The bare `tick` call is pre-existing and wants its own issue.
